// design system v2 — the storefront as built, Phase 27

Technotopia

Ranked semantic roles, two themes, five type steps, one font per locale. The stylesheet is the source of truth — every value and every ratio below is transcribed from app/globals.css, where each one carries the comment explaining why it is that number. This page is the map; that file is the territory.

Ratios are WCAG relative-luminance figures, generated from the oklch values via sRGB and rounded down, so nothing here overstates a pair. Every value was also checked to sit inside the sRGB gamut — an out-of-gamut oklch() gets clamped by the browser, and a ratio computed from the value as written would then describe a colour nobody sees.

Three ideas hold the whole thing up

Everything else on this page follows from these.

Roles, not shades

surface is whatever an elevated thing is painted; fg is whatever body copy is. A job, not a colour. That is what lets one attribute reassign the entire palette — reach for a raw gray-500 again and it will simply not flip.

One attribute, both themes

data-theme="dark" on <html> — one of the selectors HeroUI keys on, so its components flip with ours. An attribute, not a class: React owns <html className> and rewrites it on every locale switch, which would silently wipe a class a script had added. An inline script sets it before first paint, ThemeGuard puts it back after a locale switch, and ThemeToggle is the only thing that changes it — all of it in lib/storefront/theme.ts.

Storefront only

The palette is scoped to [data-scope="storefront"] on <body>. The admin tree sets neither attribute, keeps HeroUI's indigo, and stays light — its wireframes are drawn light-only, so a dark admin would be invented rather than specified.

Ranked roles — 1 of 4

Grounds

Ranked page → card → inset. The storefront's cards are grey trays recessed into the page, with no border and no shadow (--surface-shadow is transparent), so the "sunken" rank is the card fill. The dark theme keeps that order rather than inverting it the way dark-mode advice usually says: reversing it would turn every recessed tray into a raised one and change what the storefront looks like. What inverts is the range the palette sits in, not the order within it. Mutual contrast is intentionally tiny — these separate areas, they never carry text.

Ranked roles — 2 of 4

Foreground

Four ranks, body copy down to icons, shown on all three grounds because a rank has to clear AA on whichever ground it actually lands on. The ratios read surface / sunken / muted in both themes — note that in the dark theme those three run the other way, because the lightest ground is the tightest constraint for light text and there the lightest ground is surface. Each dark rank is tuned to land on the light theme's ratio against its own page ground — fg-subtle is 5.39 in both — so a component legible in light is legible here without being re-checked.

Ranked roles — 3 of 4

Lines

Both ranks sit below the 3:1 that WCAG 1.4.11 asks of a UI component's boundary. That is a deliberate carry-over of the design's hairline look, and it is only safe because a control's affordance rests on its fill and its focus ring — never on its border. Don't let a border become the only thing marking a control.
Light — darker than the ground

Ranked roles — 4 of 4

Accent — one signal blue, three tokens

Which token a thing takes is decided by one question: is the colour a fill, or is it read? Get it wrong and the dark theme fails silently — before Task 27.4, text-accent measured 2.92:1 on the dark ground, which is every link, eyebrow and focus ring on the site. Blue stays the only accent, and only on primary buttons and links.

The fill — does not flip

--app-accent-solid · bg-accent, bg-accent-solid, hover:bg-accent-hover. HeroUI's accent-filled components read --accent, so that variable stays the fill. White on it is 5.10; white on the lighter blue a dark theme reads text in would be 2.55.

oklch(0.545 0.2 258) — white on it 5.10
hover oklch(0.485 0.18 258) — white on it 6.57
The readable one — flips

--app-accent · text-accent-readable, border-accent-readable, outline-accent-readable. Text, borders and the focus ring take this one. It carries a name of its own because accent could not be it — HeroUI already owns that name for the fill.

Light — 5.10 on surface, 4.54 on sunken Dark — 6.22 / 7.02 / 7.47
On dark — never flips

--app-accent-on-dark · text-accent-on-dark. For ground that is dark whatever the theme is — a scrim over a photograph, a caption on a category card. It has to hold while the rest of the site is still in light mode, which is why it is a third token rather than just the dark theme's value.

Status — success, warning, danger, info

info is a teal-leaning cyan rather than a blue: with a blue accent, a blue "for your information" notice would read as a brand flourish rather than as a status. In the light theme each value is dark enough to serve twice — as text on a ground and as a fill under white text — which is why one token covers both text-success and bg-success. In the dark theme they are text colours only: the sole fill the storefront makes of them is StatusBadge's dot, which carries no text. Ratios read surface / sunken.

-20% light -20% dark — same fill, same label

One colour here is not a role at all: --white (text-accent-foreground, text-success-foreground …). It is the label on a solid accent or status fill, and because those fills do not flip, neither may the text on them. Anything that should follow the theme takes text-surface instead.

Type scale — five steps

Each step carries its own size, line-height, weight and tracking, so a heading is one class picked from a named set rather than four Tailwind classes reinvented at every call site. The weights step down with the sizes (800, 800, 700, 700, 600) instead of every heading landing on 800, which is what the blanket h1/h2/h3 rule this replaced did. Every step is a weight the storefront actually loads — adding a step means adding its weight to the font calls in app/[locale]/(storefront)/layout.tsx, or the browser will synthesise it. Body copy stays 400 at the browser default; the scale is for the things above it.

One font per locale

The Latin faces don't cover Persian glyphs, and Vazirmatn's Arabic subset is dead weight on an English page — so the storefront loads one sans per locale, chosen in app/[locale]/(storefront)/layout.tsx. Both faces declare the same CSS variable (--font-storefront-sans) and only one is ever applied to the tree, so nothing downstream needs to know which locale it is in. Preloading is off deliberately: Next emits a <link rel="preload"> for every font in a route's module graph, which would make /fa preload two Latin faces it never paints a glyph in.

The rules, in one place

Paint from the tokens

Never from a fixed Tailwind step. A raw bg-white, text-neutral-500, hex or oklch() literal in a className will not flip, and is the one thing that breaks the dark theme.

Fill or read — pick accordingly

bg-accent and bg-danger-solid for fills; text-accent-readable / border-accent-readable for anything read. accent-on-dark for ground that is dark in either theme.

A border is never the affordance

Both line ranks are under 3:1. A control is marked by its fill and its focus ring — 2px outline-accent-readable at 2px offset.

Cards are recessed, not raised

Depth comes from the sunken fill alone — no border, no shadow (--surface-shadow is transparent). Buttons are full pills; cards and trays are large-radius. Same in both themes.

fg-faint and the lines are for icons

The three roles that don't clear AA are marked as such in globals.css and are for chevrons, hairlines and decorative marks. Never for copy.

Adding a token

Read the block comment at the top of globals.css first, give the new value both themes, check it sits inside the sRGB gamut, quote its ratios rounded down — then update this page in the same commit.
